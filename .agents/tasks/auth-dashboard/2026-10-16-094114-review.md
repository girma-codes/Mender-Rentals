# Auth Context, Protected Routing, and Dashboard

This change wires up auth state across the app: a React context backed by localStorage, a `ProtectedRoute` guard, a sign-in flow with smart redirect, an authenticated profile dropdown in the Navbar, and a full dark-themed Dashboard page with bookings and equipment management. The implementation touches 8 files — 4 new, 4 modified — and introduces no new npm dependencies. All requirements from the original user messages are met.

Watch for: `intendedPath` is held only in React state and is lost on hard refresh; a user who navigates directly to `/dashboard` in a new tab while already authenticated will see `/dashboard` as the default destination rather than the originally intended path — this is inherent to the design choice and acceptable for a mock auth system, but worth noting. The mock login function silently accepts any credentials, which is expected.

**Verdict**: APPROVED

## High-level view

Auth state lives in `AuthProvider` (context + localStorage hydration), which sits inside `<BrowserRouter>` in `main.tsx`, making `useNavigate` safe inside the provider for the logout redirect. The `hydrateUser` function validates the parsed localStorage value's shape before restoring it, so a corrupted or tampered entry falls back to `null` without crashing.

`ProtectedRoute` saves `location.pathname` into `intendedPath` before redirecting — but this state lives in React memory, not in the URL or storage. If the user opens a protected link in a fresh tab while already authenticated (so the guard doesn't fire), `intendedPath` will be `null` and the post-login destination correctly falls back to `/dashboard`. The only gap is a direct-link visit from an unauthenticated state that triggers a full page reload before the user reaches the sign-in form; the intended path would be lost. This is a known limitation of in-memory redirect storage.

The Dashboard route is nested inside the `Layout` route, so the Navbar's authenticated dropdown is visible on every dashboard sub-view. The dashboard derives its stat counts live from the mock arrays, so the Pending Requests counter correctly decrements when Approve/Reject is clicked.

The desktop dropdown's outside-click handler uses a `useEffect` with a `mousedown` listener and a `dropdownRef`. The ref is attached to the outer container wrapping both the trigger and the menu, so clicking any menu item still fires the item's own `onClick` before the outside-click fires — no race condition.

<summary>Details</summary>

### intendedPath volatility across hard refreshes

`ProtectedRoute` calls `auth.setIntendedPath(location.pathname)` before redirecting to `/signin`. Because `intendedPath` is `useState<string | null>(null)` in `AuthProvider`, this value survives React re-renders but not a full page reload. If a user pastes a protected URL into a new tab (unauthenticated), the browser loads the page, `ProtectedRoute` fires, sets `intendedPath`, and redirects to `/signin` — all within the same session. That flow works. The loss scenario is narrower: if the browser crashes or refreshes the `/signin` page before the user submits, `intendedPath` resets to `null` and the post-login destination falls back to `/dashboard`. For a mock auth system this is acceptable. A production implementation should move the intended path to `sessionStorage` or append it as a `?next=` query param on the `/signin` URL.

### Auth persistence and shape validation

`hydrateUser` validates `id` and `email` as strings before restoring state — confirmed at lines where `parsed.id` and `parsed.email` are typeof-checked. This prevents a malformed localStorage entry (e.g., from a prior schema) from setting a partially-typed user object into state and causing downstream null-pointer failures.

### Approve/Reject desktop table omits the status badge for non-Pending rows

In the desktop Incoming Requests table, when `r.requestStatus !== 'Pending'` the Actions cell renders `<span className="text-neutral-500 text-xs">—</span>` rather than the colored status badge used in the mobile card view. The status column already shows the badge, so the dash in the Actions column is consistent — the status is displayed, just in a different cell. This is a minor visual asymmetry between mobile and desktop, not a functional gap.

</details>
