# Auth guard for 'List Your Item' and full listing form

This pass adds authentication guards to every "List Your Item" entry point and replaces the placeholder `ListItemPage` with a working form. Unauthenticated clicks set `intendedPath('/list-item')` and redirect to `/signup`; after sign-up the user lands on `/list-item` directly. The `/list-item` route is also wrapped in `ProtectedRoute` as a second layer blocking direct URL access.

All five issues from the prior review were addressed: `pendingItemId` is now persisted to `sessionStorage` (finding #2); `ItemDetailPage`'s `useEffect` includes all dependencies (finding #3); `RequestRentalModal`'s phone validator now enforces `>= 9 chars` (finding #4); `Layout.handleOpenRequestRentalModal` now sets `intendedPath` to `` `/item/${listing.id}` `` (finding #1); and `AuthContext.login` now reads `mender_phone_<email>` from `localStorage` to populate the phone field (finding #5 — closes the gap for users registered in the current session, with a residual data-integrity caveat for users registered before the key existed).

Watch for: **(confirmed)** `ListItemPage` collects a `condition` field but silently discards it — `EquipmentListing` has no `condition` property, so the value is never persisted; **(confirmed)** `ProtectedRoute` calls `auth.setIntendedPath(location.pathname)` in the render body rather than in an effect, a side effect during render that React 18 Strict Mode invokes twice and that can overwrite a previously stored `intendedPath`; **(confirmed)** the build report at `.agents/tasks/auth-guard-rental-flow/build-report.md` does not exist, so criterion #8 (zero TypeScript errors) cannot be verified from the report.

**Verdict**: NEEDS_CHANGES

## High-level view

All three "List Your Item" entry points — desktop Navbar button, mobile Navbar button, and CTABanner — route through `Layout.handleOpenListItemModal`, which checks `auth.isAuthenticated` before redirecting or proceeding. The Navbar buttons delegate to this handler via prop; CTABanner calls `useAuth` directly and mirrors the same logic inline.

`ListItemPage` is a complete form with all required fields. The `condition` field is rendered and collected, but `EquipmentListing` has no corresponding property, so the value is silently dropped when the listing object is assembled and passed to `addNewListing`. A user who selects a condition sees it vanish after submit with no indication.

`ProtectedRoute` sets `intendedPath` unconditionally in its render body. React 18 Strict Mode renders components twice in development, and concurrent re-renders can trigger the call multiple times before the `<Navigate>` commits — overwriting a `/item/:id` path stored by the rental guard with `/list-item`. The fix is moving the call into a `useEffect` with an empty dependency array.

The build report required by the review criteria was not produced, leaving TypeScript correctness unconfirmed. The `ListItemPage` submit handler constructs a fully typed `EquipmentListing` object, so a type error there is unlikely, but the missing report is a process gap.

### `condition` field collected but not persisted

`ListItemPage` declares `condition` in `FormFields` and renders a `<select>`:

```typescript
const CONDITION_OPTIONS = ['Excellent', 'Good', 'Fair'];
```

The `handleSubmit` function assembles the listing object:

```typescript
const listing: EquipmentListing = {
  id: generateId(),
  title: fields.title.trim(),
  category: fields.category as ItemCategory,
  pricePerDay: Number(fields.pricePerDay),
  description: fields.description.trim() || undefined,
  ownerName: auth.user?.name ?? '',
  location: fields.location.trim(),
  neighborhood: fields.neighborhood.trim() || undefined,
  imageDataUrl,
  createdAt: new Date().toISOString(),
};
```

`fields.condition` is not referenced here. `EquipmentListing` has no `condition` field, so TypeScript doesn't surface an error — the build passes silently. The user's selection evaporates. The fix is one-line in `src/types/index.ts` (`condition?: string`) and one-line in the submit handler.

### `ProtectedRoute` state mutation during render

```typescript
export function ProtectedRoute() {
  const auth = useAuth();
  const location = useLocation();

  if (!auth.isAuthenticated) {
    auth.setIntendedPath(location.pathname);   // ← render-phase side effect
    return <Navigate to="/signup" replace />;
  }

  return <Outlet />;
}
```

React 18 Strict Mode double-invokes this, calling `setIntendedPath` twice on mount. More critically, any parent re-render while the user is mid-redirect (before the `<Navigate>` commits) fires it again. If the user triggered the rental guard first (storing `/item/abc`), then the browser URL matches `/list-item`, a re-render of this component overwrites the stored path. The rental auto-open effect in `ItemDetailPage` would then never fire because `intendedPath` was stomped.

Moving to an effect solves both issues:

```typescript
useEffect(() => {
  auth.setIntendedPath(location.pathname);
}, []);
```

This fires once per mount, after the render, consistent with React's rules for side effects.
